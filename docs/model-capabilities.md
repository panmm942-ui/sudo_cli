# Model connections, context and routing

Capability reports distinguish **declared**, **observed** and **unknown** evidence. A profile's explicit tool, vision, reasoning, audio or streaming declaration is configuration, not a verified result. A later observation can disagree; the report retains both values and uses the observation for the current supported value. Model names do not establish any capability. Choosing a transport declares the transport to use, not successful provider support. Context capacity and reasoning levels remain unknown until configured.

Connection testing and model discovery make one explicit `GET /models` request with a default five-second timeout, cancellation and a two-MiB catalog limit. They never submit conversation content or generate a paid completion. Credentials stay in the request header, redirects are refused, and returned errors omit the upstream body. A successful catalog proves only model discovery; tool use, vision, streaming and generation remain unknown. Some compatible providers do not implement this endpoint. Their result is `unsupported-models`, not a failed generation claim. The standard catalog schema is documented in the [OpenAI model-list reference](https://developers.openai.com/api/reference/resources/models/methods/list).

Chat Completions sessions request streaming with usage reporting. Text and function arguments become Responses deltas while the upstream request is still running. Indexed parallel tool calls, namespace identities, complete arguments and usage survive translation. Custom tools carry raw input inside a JSON function envelope; that envelope is buffered until valid JSON yields the exact raw input. Executable completed tool events follow validation of the entire final response. Truncated, filtered and interrupted responses fail instead of completing tools. Providers that return JSON despite a streaming request use a buffered fallback. Providers that reject streaming must use a compatible streaming server or native Responses transport; there is no automatic repeat of a possibly charged request. The wire fields follow the [Chat Completions streaming reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events).

Native Responses monitoring passes response bytes through unchanged by default. It measures the first semantic output delta rather than headers or `response.created`, records terminal success/failure and collects reported token usage. Timing events contain request IDs and numbers, without the model, prompt, output or credentials. The health display is a recent observed heuristic; it separately exposes first-output latency, total latency, error rate and generation tokens per second. Generation speed uses provider-reported output tokens and time after first output; it remains unknown when either is unavailable. Buffered fallback timing measures full-response latency. This is not a network bandwidth measurement or a service availability guarantee.

Both adapters accept `toolsAllowed` (default `true`) and an optional exact `toolAllowlist`. An absent allowlist permits all advertised tools; an empty list permits none. Disabling tools removes definitions and tool choices and rejects executable function, custom, hosted and MCP output. Restricted native SSE frames are inspected before their original bytes are forwarded; rejected frames emit no executable completion. Individual frames and JSON responses are bounded to 16 MiB. Allowed native events retain their exact bytes. `getToolCatalog()` returns only the latest advertised identifiers: converted wire names for Chat Completions, actual `namespace.name` for native namespaced functions/custom tools, and declared type IDs for unnamed hosted tools. Matching namespace leaves and ambiguous collisions cannot broaden an allowlist. The [Responses function-call and namespace reference](https://developers.openai.com/api/reference/resources/responses/methods/retrieve) documents the separate namespace and name fields.

`onPolicyError({code,message})` reports `TOOLS_DISABLED` or `TOOL_NOT_ALLOWED` with a fixed sanitized message, once per rejected response. It is a notification and is not awaited; synchronous or asynchronous callback errors leave the output rejected. Background native tasks immediately interrupt and reject with `APPROVAL_REQUIRED` on this callback or an out-of-scope native approval. Background settings retain exact tool permissions, writable folders and up to 16 explicit acceptance checks. Capabilities belong to the selected connection; local guardians do not inherit working-model declarations. Known capacity is checked before startup using the estimated fresh input, developer instructions and a 4096-token reserve. Unknown capacity accepts the bounded fresh input. Explicit `reasoning: false` rejects a requested effort, and `hostedSearch: false` disables native hosted search. Hosted search and training appear independently as declared, observed or unknown evidence; these declarations do not verify provider behavior.

Budget hooks run before every outbound generation. `beforeRequest({id,model,transport,inputTokensEstimate,maxOutputTokens,estimated:true})` may return `{maxOutputTokens,timeoutMs}` to cap tokens and time. Rejection prevents the fetch. `onUsage({id,model,transport,inputTokens,outputTokens,totalTokens,estimated:false})` receives only valid provider-reported usage. `afterRequest({id,model,transport,outcome,durationMs})` settles every admitted request, including errors, cancellations and responses missing usage. Hooks are awaited and accounting failures stop the transport; missing usage remains the ledger's reserved estimate. Public errors are sanitized. Hooks can be supplied together as `requestHooks` or as individual callbacks.

Context preflight keeps a complete archive separate from the model input. Token estimates use UTF-8 bytes divided by three plus message framing and are labeled estimates; images, tool catalogs, provider framing and tokenizer differences can change the real total. The allowance includes an explicit output reserve and a ten-percent margin. Unknown capacity returns `needs-capacity` so the caller can request a value. History beyond the estimated allowance returns `needs-review`, without dropping any messages. A bounded replay requires an explicitly reviewed nonempty summary plus selected message indices. The returned summary is user conversation content, not system instructions. A reviewed selection that still exceeds capacity returns `over-capacity`. The canonical saved archive remains complete in every outcome.

Automatic model routing is disabled by default. Manual profile selection always wins. For tasks explicitly marked simple, optional `cheap` routing ranks configured models using user-supplied input/output token prices; optional `local` routing selects a loopback endpoint. Complex work stays on the current model. Required capabilities must have explicit supporting evidence on alternatives, and unknown capability/price metadata produces a current-model fallback. Routing returns the chosen profile and rationale; it does not modify saved settings, infer competence from a model's name, or promise an actual price.

Public modules: `provider-capabilities.mjs` (`capabilityReport`, `discoverModels`, `probeConnection`), `context-manager.mjs` (`estimateContext`, `preflightContext`) and `model-router.mjs` (`routeModel`).
